# book-recommender

One book recommender in two versions, on the Book-Crossing ratings in `datasets/`.

| Folder | What it is | Rule |
|---|---|---|
| `v1/` | The version Miloš built by hand, November 2025 to early 2026: EDA, user- and item-based CF, content-based filtering, the FastAPI app, the report. | Frozen. Never edit, move, reformat or fix anything under `v1/`, not even a typo or a broken path. |
| `v2/` | The version built from October 2026. | All new work goes here. |
| `datasets/` | `Books.csv`, `Ratings.csv`, `Users.csv`, shared by both versions. | Read-only. |

Tag `v1.0` is v1 in its original layout, before it moved into `v1/`. A problem found in v1 is
written down and fixed in v2, never in v1. `.claude/settings.json` denies the file tools on
`v1/` and `datasets/`; scripts can still write there, so this rule is what holds.

## v1 facts that matter for v2

- The live API (`what-else-should-i-read.fly.dev`, Fly app `what-else-should-i-read`) serves the
  book demo on cassiopeiai.com. It needs `item_encoder.pkl`, which is not in `v1/models/`
  (`*.pkl` is gitignored). The encoder is only the 2,508 training titles in sorted order, so it
  can be rebuilt exactly: `bookrec.data.load_split().titles`.
- The API's table (`v1/models/topk_item_sim.npz`) holds raw dot products; v1's notebook
  evaluated cosine. Phase 1 rebuilds the table from v1's code and checks it is identical.
- The notebooks load the data from the absolute path of the machine they were written on, so
  they don't run as they are. v2 reads `datasets/` by a relative path.

## v2

Run from `v2/` with its venv: `pip install -e ".[test]"`, `pytest`, `python -m bookrec.evaluate`.
Every v2 model is scored on v1's split from `bookrec.data.load_split()` (made by v1's code);
`tests/test_v1_reproduction.py` pins its fingerprint and v1's numbers, and must pass before the
pinned library versions move. From stage 2 on, models use `bookrec.books.clean_split()`: the
same ratings and halves with books identified properly; `tests/test_books_on_data.py` pins
its reviewed counts, so a rule change means regenerating and reviewing `v2/data/books.csv`.
Reports in `v2/reports/` and `v2/data/books.csv` are generated by `python -m bookrec.evaluate`;
change the code, not the outputs. Each stage is a branch, merged after review.

From stage 3, models train on `bookrec.interactions.load_interactions()`, under one rule:
training may use any Book-Crossing interaction with the 2,405 books, by any user, rated or
not, except one that covers a held-out user and book through any edition
(`tests/test_interactions_on_data.py` checks it). A book a user has in training, rated or not,
is never recommended to them. Settings are chosen only on `validation_split()`, never on the
held-out ratings, which score each chosen model once; widen a grid whose best sits at an edge.

The demo on saricmilos.com (`/projects/book-recommender`) runs with no server: `python -m
bookrec.export` writes its data, from the settings in `v2/reports/phase3-models.json`, into
the site's `src/content/book-recommender/` (`BOOKREC_SITE` names the site's folder, else
`C:\dev\sites\saricmilos.com`). Re-run it after any change to the model or the books, and
commit the result in the site's repository; pushing the site's `main` deploys it (Vercel), so
that waits for Miloš. Two display rules live there, not in the model: one edition per list,
and Wild Animus never recommended.

Book details come from Open Library once: `python -m bookrec.openlibrary` (about 45 minutes,
1 request a second) writes `v2/data/book_details.jsonl`, which is committed; its raw responses
are cached in the gitignored `v2/data/openlibrary-cache/`, so a re-run is offline and fast.
Nothing else may call the network. Requests identify the project by its GitHub URL only,
never a personal email.
